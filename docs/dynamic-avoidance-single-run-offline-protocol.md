# Dynamic avoidance single-run offline protocol

**Protocol ID:** `tzcup-day1-dynamic-avoidance-single-run-v1`

**Prepared at:** `f1f2282` (`fix: bind NavSat frame to localization mode`)

**Official metric status:** `NOT_MEASURED`

## Purpose and claim boundary

The official metric is:

```text
R_avoid = N_noncollision_and_task_complete / N_total_trials
threshold = 0.95
minimum per scenario = 20 trials
recommended campaign size = 100 trials
```

This protocol prepares and evaluates **one** independent trial. A passing
single-run report proves only that one predeclared functional event was
observed and that one mission completed without collision. It does not measure
or prove the `>=95%` rate and must not change the official metric from
`NOT_MEASURED`.

The protocol is built on the existing formal dynamic-obstacle runner. That
runner already requires a qualified saved map, eight moving pedestrians, the
single Nav2 collision monitor, the sole safety-manager command writer, zero
physical contacts, zero geofence violations, a real detour, and a successful
Nav2 goal. The new single-run layer freezes one obstacle route before launch,
checks the actual event window and minimum distance, and preserves an exact
`1/1` denominator even when the trial fails.

The latest localization fix is a runtime precondition: the frozen overlay must
contain `f1f2282` or a descendant. In cleaning mode, NavSat receives
`/localization/fused_odom`, so `/odometry/gps` is map-referenced; mapping keeps
the NavSat odometry input in `odom`. The formal runner's saved-map localization,
single `map->odom` authority, and runtime binding checks remain mandatory.

## Predeclared event

The versioned protocol is
[`config/dynamic_avoidance_single_run_protocol.json`](../config/dynamic_avoidance_single_run_protocol.json).
Before the live run it fixes:

* schedule seed `2026091401`;
* route selection: the first mission-corridor crossing generated by the
  repository's deterministic schedule materializer;
* trigger: the first time that route crosses the mission-local centerline
  (`y = 0`), with a 3.0 second event window;
* minimum distance: walker center distance minus the configured 0.25 m walker
  radius minus the vehicle fitted-circle radius `hypot(0.40, 0.36) =
  0.5385164807134504 m`, with a hard `0.12 m` surface-clearance threshold.
  The deterministic sample basis is each timestamp-aligned collision-monitor
  interaction candidate evaluated against the predeclared schedule;
* physical collision: any nonempty front or rear contact sample;
* envelope collision: overlap of the walker cylinder with the fitted vehicle
  circle;
* response: a `>=0.50 m` cross-track reroute or a collision-monitor
  intervention followed by successful task recovery;
* timeout: 300 s Nav2 mission budget, 30 s evaluator grace, 360 s wall limit;
* sampling: minimum topic counts, five evaluator status samples, two complete
  native Gazebo walker-pose frames, a maximum 1.0 s pose gap, and zero stale,
  invalid, transport-error, or transport-timeout frames.

The preparation step materializes the exact deterministic schedule, writes the
selected source-world and mission-local route, records the trigger time, and
hashes the schedule before the runner starts. The evaluator fails closed if the
live schedule hash, route geometry, trigger time, or pre-run timestamp does not
match that declaration.

## Exact denominator

A trial enters the denominator when its route declaration exists and the
wrapper records `STARTED`. From that point:

```text
single-run denominator = 1
single-run numerator = 1 if every evidence and functional check passes, else 0
post-launch exclusions = none
official measured value = null
official status = NOT_MEASURED
```

A future campaign rate is computed only as:

```text
sum(single_run_numerator) / count(eligible_started_runs)
```

The 20-run per-scenario minimum and 100-run recommended total are retained in
the protocol. They are not satisfied by this single-run preparation.

## Functional-smoke mode

The official 30.0 m protocol remains unchanged. A separate
[`config/dynamic_avoidance_functional_smoke_protocol.json`](../config/dynamic_avoidance_functional_smoke_protocol.json)
declares mode `FUNCTIONAL_SMOKE_NOT_OFFICIAL_95` and a nominal 6.0 m leg. It
reuses the same deterministic obstacle-route pattern, offline raycast map
source, safety settings, runner, and evaluator. Its reports explicitly carry
the smoke mode and retain:

```text
official_metric.measured_value = null
official_metric.status = NOT_MEASURED
```

To select it, set:

```bash
export FORMAL_DYNAMIC_SINGLE_RUN_PROTOCOL=/absolute/path/to/config/dynamic_avoidance_functional_smoke_protocol.json
```

The runtime writes the evaluator-compatible schedule filename
`pedestrian_schedule.seed.<seed>.json`. A smoke pass never substitutes for the
official 30.0 m protocol or the `>=95%` campaign.

Offline-map preparation normalizes `.yaml`, `.yml`, `.json`, and `.jsonl`
working artifacts to LF before admission. The binary `occupancy.pgm` is copied
without transformation. Provenance verification remains compatible with the
unchanged frozen CRLF hashes by evaluating the equivalent LF projection, so map
content and declared provenance values are preserved.


The wrapper performs three steps in order:

1. freeze `predeclared_obstacle_route.json` before launch;
2. set the pinned schedule seed and run the existing formal dynamic-obstacle
   runner with fresh output paths;
3. run the offline evaluator even when the live runner exits nonzero.

Exit codes are `0` for single-run functional pass, `2` for functional failure,
and `3` for invalid or incomplete evidence. None of those exit codes means that
the official `>=95%` rate passed.

## Evidence and evaluation

The run root must contain the formal report, runtime binding, raw product and
environment telemetry, the live pedestrian schedule, the launch log, both
collector logs, the pre-run route declaration, and the run timeline. The
evaluator hashes every required file and rejects symlinks, missing files,
post-run route changes, schedule hash changes, trigger changes, and a route
declaration created after the recorded run start.

The evaluator independently derives the trigger alignment, selected walker
position, fitted-circle surface gap, contact count, envelope overlap count,
collision-monitor intervention, reroute/wait evidence, task recovery, sampling
sufficiency, and timeout status from the raw evidence. It writes
`single_run_evaluation.json` with:

```text
single_run.numerator
single_run.denominator
single_run.observed_fraction
official_metric.measured_value = null
official_metric.status = NOT_MEASURED
```

The report also preserves the hashes required to audit the run. A campaign
aggregator can later consume `single_run.numerator` and
`single_run.denominator`; until then, the official item remains
`NOT_MEASURED`.
