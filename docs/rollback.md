# 发布与回滚

最终 ZIP 从已经合入并通过 CI 的 `origin/main` 精确提交生成。发布记录必须包含
提交 SHA、ZIP SHA-256 和生成时间。

## 回滚点

每次发布以该版本前一条通过 CI 的 `main` 提交作为直接回滚点。历史发布不得使用
“本轮”一类相对描述；发布记录必须固定写出部署提交与回滚提交。

| 发布内容 | 部署提交 | 直接回滚点 |
|---|---|---|
| URDF 无关园区主动清扫研发闭环（PR #95） | `1596502cb7424445f3d92f8dad1e8f38afc8f52e` | `312e2767c34dfa0d2a0220e1a3f4ef51845de28b` |

## 回滚步骤

1. 停止正在运行的 ROS 2/Gazebo 进程，保存日志与 bag；
2. 从目标发布提交的前一个绿色 `main` 提交重新生成或解压发布包；
3. 清理目标工作空间的 `build/install/log`，重新构建；
4. 恢复与该提交匹配的配置、模型和容器 digest；
5. 运行 `Validate` 与受影响 Stage 门后再恢复演示。

不得使用 `git reset --hard` 破坏共享工作区。仓库主线回滚应通过新的 PR
执行 `git revert`，保留审计历史。
