# RDK S100P 实车硬件 Bring-up 合同

生效日期：2026-08-30。此文件把 S100P 板端计算与实车 I/O 的边界落实为可执行的
bring-up 清单。它不授予任何执行器控制权限，也不替代实验室安全规程、设备厂商手册或
人工现场负责人批准。

当前状态：`NOT_READY_FOR_REAL_ACTUATOR_COMMANDS`。

## 1. 范围、事实边界与关联文件

本合同仅针对已连接的 **D-Robotics RDK S100P** 作为车载计算板。已验证的 S100P
身份、TROS/ROS 软件包、BPU 推理或产品 ROS 图，只能证明计算链可用；它们不证明
底盘、机械臂、刷盘、泵、阀、传感器或安全链已经接线、安装或受支持。

截至本合同编写时，项目中没有可指向已安装实物的底盘/机械臂/刷盘/泵硬件驱动适配层。
`mock_components/GenericSystem`、`gz_ros2_control/GazeboSimSystem` 和 Gazebo 插件均
是仿真实现，不能接管真实执行器。

实施者必须先以以下文件为逻辑接口参考，并为每个实际设备补齐独立的型号、接线、总线、
电气额定值、固件与驱动证据：

| 领域 | 现有逻辑参考 | 实机缺口 |
| --- | --- | --- |
| 任务级速度/刷盘话题和超时 | `starter_ws/src/sanitation_tasks/config/hardware_interface_contract.yaml` | 实物底盘/刷盘反馈与硬件接口插件 |
| ros2_control 关节模型 | `starter_ws/src/sanitation_vehicle_description/urdf/high_fidelity/control_interfaces.xacro` | 每个总线的 `hardware_interface::SystemInterface`、反馈与故障处理 |
| 仿真执行器/接触 | `starter_ws/src/sanitation_gazebo_control/` | 不可复用为真实 I/O；需厂商协议和驱动 |
| 整车软件安全状态机 | `starter_ws/src/sanitation_safety/sanitation_safety/whole_vehicle_safety_core.py` | 实体急停、安全继电器、驱动禁能与独立测量证明 |
| 整车静态布置 | `config/high_fidelity_vehicle/`、`docs/formal-vehicle-real-world-build-readiness.md` | S100P 实物安装尺寸、线束、载荷和制造放行证据 |

详见 [S100P 板端优先边界](s100p-board-first-execution-boundary.md)。若本合同和任何
运行脚本冲突，以更保守的安全限制为准。

## 2. 分阶段放行表

每一级完成后都必须归档证据，且由现场负责人显式签字放行下一等级。一个 ROS 话题存在、
发布零值或服务可调用，都不是安全放行证据。

| 等级 | 可做工作 | 必须满足的门 | 本级绝对禁止 |
| --- | --- | --- | --- |
| G0：计算/只读 | 板卡身份、系统、包、模型、BPU、网络、传感器枚举；离线/回放推理 | 不接入执行器命令线；记录只读命令和原始输出 | 所有执行器命令、自动任务 |
| G1：接口建档 | 在断开驱动使能条件下核对 CAN/串口/以太网/USB、设备序列号和只读遥测 | 逐设备接线图、额定值、驱动来源和 frame/node ID 已复核 | 猜测接口后试转、试泵或试夹爪 |
| G2：硬安全链 HIL | 只验证急停、继电器、接触器、使能回路和故障反馈 | 实体急停、独立安全继电器、默认断能、人工断电路径均已实际测量 | 用软件 `/emergency_stop` 替代实体安全链；旁路继电器 |
| G3：传感器 HIL | 相机、雷达、IMU、GNSS、编码器只读采集、时间戳/TF/标定检查 | 物理设备可识别、话题率/时钟/外参记录；不允许被控制闭环使用 | 用未标定传感器驱动底盘、机械臂或刷盘 |
| G4：逐执行器 HIL | 在隔离工装中做低风险单通道命令与反馈一致性测试 | G0–G3 全部通过；对应驱动、限位、禁能和停止测量均有效 | 多执行器联动、自动规划、载人或开放场地运动 |
| G5：受限整车 HIL | 低速、人工监护、无清扫/无抓取的受限闭环 | 每个单通道验收通过；独立观测可证明停止距离与故障降级 | 无人值守、随机行人场景、RL/导航自动任务 |
| G6：任务前现场验收 | 在批准场地做逐项功能验收 | 完整 HIL 证据、风险评审、回滚包和现场批准 | 将未验收机构并入比赛/正式清扫任务 |

## 3. G0–G3：当前可以完成的只读工作

G0/G1/G3 可以在 **不控制真实执行器** 的情况下执行。每次记录实际运行的命令、操作者、
UTC/本地时间、S100P 系统版本、git revision 和文件哈希；不得把此前的探测结果复制为
本次证据。

- 核对 `/proc/device-tree/model`、`compatible`、系统镜像标识、OS/内核、**TROS/ROS
  setup 文件是否存在（主采集进程不 source；仅允许固定 allowlist setup 在隔离子进程中为三条 ROS
  list 命令 source）**、BPU runtime/工具版本或 `ABSENT`、相关 dpkg
  包和模型文件的路径/哈希；G0 不执行模型推理。
- ROS 仅允许 `ROS2CLI_DISABLE_DAEMON=1` 的 `ros2 pkg list`、`ros2 node list --no-daemon`
  和 `ros2 topic list -t --no-daemon` 只读清单。禁止 ROS 发布、服务调用、action、参数写入
  或启动节点；`ros2` 不存在同样记为 `ABSENT`。
- 只读列出 `/dev/video*`、`/dev/tty*`、`/dev/can*`、网络接口、USB 枚举、已安装 ROS
  驱动包及其版本；未出现的设备记为 `ABSENT`，而不是“默认可用”。
- 每个实际设备建立一张硬件卡：厂商和型号、序列号、供电、保险/断路、最大电流、通信
  协议/速率、主从 ID、物理 frame、线束/接口图版本、厂商驱动来源及许可证。
- 传感器只录制原始话题、消息类型、频率、时间戳单调性、时钟偏差、frame_id、外参/内参
  标定版本和掉线计数。G3 成功不允许发布非零控制量。

G2 必须通过实际断能测量，而非 ROS 日志。最低要求：急停为常闭安全回路；上电默认禁能；
安全继电器/接触器切断驱动功率或使能；独立人工可触达断电方式；安全 MCU/继电器故障
或心跳丢失时断能。必须记录触发点、测量工具、接触器/使能信号、驱动实际失能状态和
从触发到静止的时间。逻辑安全状态机可作为附加监控，不能成为唯一保护层。

## 4. G4：逐执行器 HIL 顺序

以下顺序是最小安全顺序，不是自动执行脚本。每一步都需要对应设备厂商手册、现场负责
人批准、隔离区和人工监护；任一异常立刻使用实体急停，回到 G2 排查。

1. **底盘与转向**：车轮悬空或使用经批准的约束工装，机械臂收纳、刷盘/泵/阀禁能。先
   只读确认驱动器状态、编码器方向、制动/转向限位和零速度反馈；随后只做单轴、受限的
   极低速命令一致性测试。记录命令、速度/位置/电流/温度反馈、方向、限位及断能停止。
2. **机械臂与夹爪**：底盘断能，工作空间清空，机械限位、软限位、零位和碰撞模型与实物
   对照。先读状态，再从近基座到末端逐轴低速、小行程测试，最后单独测试夹爪开合。禁止
   IK 轨迹、抓取、投箱、载荷和多关节运动，直至各轴停机/限位/失联故障均有实测证据。
3. **刷盘、滚刷、升降、刮吸**：底盘和机械臂禁能，刷具离地或使用合规工装。先验证升降
   限位与位置反馈，再验证单刷低速、方向、电流、振动、失能停止；刮吸机构同样逐通道。
   禁止与地面接触的清扫和任何自动刷盘联动。
4. **泵、阀、污水/干垃圾机构**：先以空载或厂商允许的安全测试介质核对方向、流量/压力、
   漏液、液位/满箱和超流保护；真实积水回收只能在容器、泄漏防护和人工监控到位后进行。
   不允许用假遥测替代液位、泵故障或接触器失能证据。
5. **安全回归**：对每一个已放行通道分别在静止和受限运行状态触发急停、心跳丢失、驱动
   故障和传感器掉线。所有通道都必须回到实际无能量/安全状态，而不只是 ROS 状态变更。

单通道验收通过的最低证据：真实硬件身份、驱动版本与配置哈希、接线/ID 对照、命令上限、
命令与反馈时间序列、功率/使能信号、故障/急停结果、现场照片或视频索引、操作者和复核人。
没有原始遥测的口头确认不可计入 G4。

## 5. 禁止动作（在相应门未通过前）

- 未通过 G2 时，禁止发布或桥接任何非零 `/cmd_vel`、机械臂轨迹、夹爪、刷盘、升降、泵、
  阀、排水或垃圾箱机构命令；禁止让驱动器带电试探方向。
- 未通过该通道的 G4 时，禁止该通道与任意其他通道联动；禁止使用 Nav2、RL 策略、抓取
  策略或清扫状态机生成真实控制命令。
- 未通过 G5/G6 时，禁止无人值守、开放园区、动态行人、真实脏污/积水清扫、真实垃圾抓取
  与投箱，以及任何比赛式全任务演示。
- 永远禁止旁路实体急停/安全继电器、篡改硬件限位、以仿真 topic、手写 JSON 或软件“急停”
  声称实体安全合格。

## 6. 证据包合同和放行判据

每一次门评审应创建一个不可覆盖的证据目录，例如
`artifacts/s100p_hardware_bringup/<session>/<G0-G6>/`，至少包含：

```text
manifest.json                 # session、时间、操作者、复核人、git revision、SHA-256
board_identity.txt            # model/compatible/OS/kernel/ROS/TROS/BPU 只读输出
hardware_inventory.txt        # 设备节点、总线、USB/网口和 ABSENT 项
device_cards/                 # 每个设备的型号、序列号、供电、接线和驱动来源
safety_measurements/          # 急停/继电器/接触器/停止时间原始测量
telemetry/                    # 命令、反馈、故障、温度、电流/压力/液位等原始数据
calibration/                  # 传感器内外参、TF、时间同步与版本
operator_log.md               # 环境、工装、风险、异常、退出和签字
```

`hardware_interface_contract.yaml` 的 `hil` 阈值（命令 p95、急停延迟、传感器掉线率）是
**任务层验收下限**，不能替代更严的设备厂商额定值或安全规程。证据包必须同时给出其
测量方法和原始数据；若任一通道缺少真实驱动、设备身份、安全测量或反馈，则状态保持
`BLOCKED`，不得以模拟结果或计算节点成功代替。

## 7. 实施完成定义

本合同本身完成的定义仅为：团队可以按上述清单安全地准备和记录 bring-up；它不表示任何
实机功能已完成。只有在特定设备的驱动、接线、安全链、单通道 HIL、受限整车 HIL 和现场
验收均形成对应证据包后，才能将该设备从 `BLOCKED` 更新为已放行。
